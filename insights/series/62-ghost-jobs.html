62 查无此人：两张同号的工单，与一场没有终点的等待

2026-09-14·连载

0. 现场：停在第 2 个单元的补跑作业

08:53:58，补跑作业发上 win-node——562 个工作单元（asr_retry 4 + extract_retry 14 + vlm_stale 17 + ocr_need 527），编号 job-153，把昨夜采集欠下的零头补齐。

08:54:13，脚本处理完前两个单元，向队列提交新一轮 ASR 工单。然后，停表：进度冻结在 done=2/562，时间戳 08:54:23，日志尾巴再没长过一个字。

查它的状态：running。进程死了吗？没有——后来取消它，taskkill 要 rc=0 才收场。它活着，在等：等一个永远不会出现的号。

1. 捞证据：出生证明与查无此人

先翻账本（jobs.json）：153 在、154 在、155——没有。再翻审计（audit.jsonl）。审计是逐行追加的，不参与读-改-写，正好是事故考古的地基：


[09-14 08:54:13] agent  job_create  job-1789347253-154  queued asr
[09-14 08:54:13] agent  job_create  job-1789347253-154  queued asr   ← 同一秒、同一个号、两条
[09-14 08:54:13] agent  job_create  job-1789347253-155  queued asr   ← 这条的账本条目，后来没了

一秒钟里三张工单进队，发出两个号。审计条条在案，账本最后只认一张：154 的幸存者 admit（调度准入，08:54:15）、跑完（08:54:21，rc=0）。另外两张被写丢了——其中一张就是采集器正在等的号。账本上，查无此人。

判据一行：审计有出生证明、账本查无此人、消费者永远在等——命中。

2. 三根因

① 号是数出来的，不是发出来的

编号规则一行：


job = {"id": f"job-{int(time.time())}-{len(jobs)}", ...}   # 算 ID
jobs.append(job)                                            # 入账
save_jobs(jobs)                                             # 存回

len(jobs)——"账上现在有几条"。这读的是一份别人也在改的状态。事故里的链条恰好把两个坑串了起来：第一张单刚追加，就被一次晚到的存回抹掉（见②），长度退回 154；下一个提交者读到 154，于是又发出一个 154。号不是被发放的，是从共享状态里推出来的——推的依据刚被人倒带过。

② 读-改-写没有门

45 之后，这块代码的每一次回写都长成了"重读→只改自己那几格→存回"：


fresh = load_jobs()                                      # 读
cur = next((x for x in fresh if x["id"] == job_id), None)
cur["log_tail"] = list(recent)                           # 改（只改自己那几格）
save_jobs(fresh)                                         # 写

单看每一处，都是好公民。但"读"和"写"之间隔着一个窗口，而 1.6.0 起队列多作业并行，这本账上同时活跃着多路写者：日志泵（长作业每行输出回写一次）、建单、调度器（admit 改状态）、收尾（终态+rc）、异常兜底。两个人同时读，一个先存，另一个后存——后存者手里那份世界，不含先存者刚放进去的东西，于是天经地义地把它删掉了。

45 的窗口有十二分钟（长作业的旧快照），肉眼可见"队列倒退回十二分钟前"；这一次的窗口只有几十毫秒——但写者够多、够密，回退虽小，够把一张刚建的单退回不存在。"长度 154→155→154"这样的小数退格，就是倒带的指纹。

1.6.0 之前没炸，不是没有洞——是路上没人。单写者不会和自己丢更新；写者一多，毫秒级的窗口就成了每天都有人的门。

③ 等待没有截止（消费侧）

采集器等的那个号不会回来。它的等待循环里查不到号就再等五秒——v6 的代码里没有"缺席"这个概念：不计数、不判死、不留痕。对一次等待来说，"对面出事了"和"对面慢"应该是两回事，而区别只能由截止来画。 顺带一枚小钉子：它本地用 {号: 工单} 记在途——号若不唯一，字典自己会静默覆盖，"我在等谁"都会失真。这颗钉子的根在①，①修好，钉自落。

3. 修复：门与截止

内核 1.6.5（98d8738）——给读-改-写装门。 _jobs_lock 升为 RLock，包裹全部八个 load→改→save 回写站点（建单、调度、PID 入账、日志泵、模型兜底、收尾、异常、取消）。门内长这样：


with _jobs_lock:            # 读-改-写整段，同一扇门
    fresh = load_jobs()
    cur = next((x for x in fresh if x["id"] == cand["id"]), None)
    if cur is None or cur["status"] != "queued":
        continue
    cur["status"] = "running"
    save_jobs(fresh)

建单也在门里，注释把意图写死：


with _jobs_lock:  # ID 序号=len(jobs)，整段持锁保证「算 ID→入账」不被并发写者穿插

——号从"数出来"变成"发出来"：算号、入账、存回在同一扇门里完成，门外的写者只能看到"还没发"或"已发好"。save_jobs 同时升级为原子写（tmp+replace，读者永远看不到半写文件）——这笔顺手的升级欠出了下一篇（63）。代价写明：每次回写变成门内整表读写，写者互相排队，用吞吐换正确。

采集器 v7——给等待装截止。 两条：整体死线 1800 秒；缺席看门狗——连续 12 次（≈60 秒）在账本里查无此号，判死，写 job_lost 终态，继续下一件。幽灵不再能扣住整条产线。

现场处置：取消 job-153（taskkill rc=0）。

4. 活体验证：让同一秒再来一次

09:10:00，同秒两发 ASR 工单——这一次正确分号 job-1789348200-157 / -158，双双 admit、双双跑完。同秒、同长，不再同号。

重发的补跑作业随后开工。它会在 55.4% 处撞上新的一笔债——那是 63 号。

5. 收束

  • 号要来自保证。 编号不能从"读到的状态"里推——"秒 + 列表长度"看着够唯一，实则拿共享可变状态当了计数器。锁内发号（或单调计数器、UUID），一句话的事；事后追两张同号的单，一上午。
  • 读-改-写的整段，才是要保护的东西。 reload-modify-save 把窗口从十二分钟缩到毫秒——它对，但不完整：窗口缩小不等于没有窗口，只等于需要更多人经过才撞上。 A066 的下一行：重读→只改自己那几格→存回，且整段不可被穿插。写者变多的那天，就是"毫秒窗口也会被撞上"的那天。
  • 等待必须有截止。 幽灵 ID 不会自己出现；对缺席要计数、要判死、要留痕。一次没有终点的等待，在监控上和死机长得一模一样。
  • 审计救了这一天。 账本是读-改-写的（会丢人），审计是 append-only 的（只会变长）。"谁在几点几分出生过"全在审计里——给共享状态配一本只会变长的旁证，是最便宜的事后保险。

（第三笔账：1.6.5 顺手的原子写，在 Windows 上撞了一堵句柄的墙——重发的补跑作业在 55.4% 摔倒，63 号见。）
