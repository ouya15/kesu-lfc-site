37 查房：工牌之后的越权审计

2026-09-13·连载

前情：16《给 agent 发 token》说"治理的最后一公里是发工牌"；20《OpenAPI 是 agent 的说明书》补了"契约不死，agent 自来"；36《拒绝面》刚把"机器说不"编译成语法。这一篇把最后一段接上：说不之后，要记住"谁试过"。

一句话：拒绝要留痕、留痕要可查；查房不是翻流水，是一张聚合的脸。

引子：一个 401，和一个 403

补治理面的时候，发现一个安静的缺口。

"没戴工牌被拦"（401）从上线起一直在留痕——审计表里躺着 14 条；而"戴着工牌走错房间"（403），代码里直接返回，一条痕都没有。

这恰恰反了。401 是守门的正常动作，是噪声；403 才是信号——它要么说明权限设计错了，要么说明某个 agent 的行为偏了。有工牌的越权，是内部人风险唯一的早期形态。 补完当天，审计表里 401:14 / 403:2——那两个 2，就是刚才测试时"故意走错房间"留下的。

1. 审计的目标不是「全记」，是记对

很多系统只审计成功操作。那等于只拍了"干成的事"，漏掉"想干没干成的事"——而治理要的恰恰是后者。

所以两类拒绝要分开看：没牌被拦是系统健康的证明，噪声，计数即可；有牌越权是待解读的信号，要带全上下文（谁、哪扇门、缺什么权限、什么时候）。审计设计的第一步不是"记多少"，是"哪几类值得记全"。

2. scope 收拢成一张表

越权要记全，前提是"越权"有唯一口径。原来的写法是每个接口里手写一行角色检查——检查散落的地方，必然有漏网、必然口径漂移，而且下一个加接口的人（可能是 agent）只能靠模仿。

收拢成一张表：

动作允许角色
判过 / 四态user, admin
笔记上报agent, admin
立项agent, admin
审计读取admin

配一个统一的裁决函数，所有接口的 403 都从它走。一处声明、一处改、漏一处编译器都会先看出来。

3. 查房报告 ≠ 流水尾

查房视图里放什么，是一次刻意的减法：拒绝按 401/403 分组计数、写操作按"谁×干了什么"聚合、最近明细各留一批。不做留存期管理、不设花哨过滤，最近 200 条封顶。

理由还是那句：为不存在的问题付费是最贵的税。翻事件流是考古，报告才是查询——20 条聚合比 2 万条流水有用得多。

4. 查房的门，也能被查房

有一个让设计闭环的小细节：普通用户访问查房页 → 403。而这条 403 本身，也落进审计表。

连"拒绝查房"这件事，都被记录在案。 拒绝面自证：没有任何一条越权尝试会凭空消失。

5. 验收与边界

四条验收句，全是可复现的：直删 → 403 且理由可读；越权上报 → 403 且留痕；管理员查房 → 聚合+明细；普通用户查房 → 被拒且留痕。外加一条回归：旧门店（另一个前端）经 user token 的读写路径全部照旧——收紧的是越权面，不是正常面。

结语

工牌（16）→ 说不（36）→ 查房（37）。治理的完整闭环不是"发权限、拦越权"，而是：发权限、拦越权，并且让每一次拦截都成为下一轮设计的证据。

agent 是有能力、低成本、无监督、失忆的操作者——所以每一块工牌后面，都该有一张查房表。它不防人，它防遗忘。
