61 短路的账：缓存省掉的一次计算，与九十九小时的空缺

2026-09-14·连载

0. 现场：一个上午，两本对不上的账

2288 件视频、四路信号、过夜跑完，晨间复审。第一件事是算总账——把逐条结果的时长加一遍：

756.3 小时。 而首跑逐件加总是 855.5 小时。同样的 2288 件，账上少了 99.1 小时。

同时浮出来的还有第二笔：手上有个更老的基准数字 848.8 小时（旧台账），跟新数字、跟 855.5 都对不上，差 6.7。

两笔差额里，一笔是数据在劣化，一笔后来查明是尺子的问题。先查大的。

第一刀很快：756.3 这边，339 件 dur_s=0——时长为零。而且不是随机零散：它们整齐地属于同一类件——Jellyfin 报不出运行时长的那一批。这一条线索就把方向指死了：这些件的时长，本来该由别处算出来。

1. 解剖：被短路跳过的那一行

时长有两条来路：首源是 Jellyfin 索引里的 RunTimeTicks（枚举清单时白拿）；兜底是 ffprobe 现测——留给 Jellyfin 报不出的那 339 件。兜底计算长在抽帧函数里：


def extract_frames(it, ffmpeg):
    d = item_dir(it)
    if not os.path.isfile(os.path.join(d, "media.json")):  # 还没有格式档案 → 现测
        probe_media(...)                                   # v8 起顺手记下 dur_s
    if os.path.isfile(os.path.join(d, "f.done")):
        return True                                     # ← 短路：缓存命中，直接返回
    ...
    dur = it.get("dur_s") or ffprobe_duration(ffmpeg, it["path"]) or 0   # ← 兜底时长，在短路之后
    if dur:
        it["dur_s"] = round(dur, 1)

单件处理逻辑没有错：没有缓存的件走完整路径，时长算得妥妥的。问题出在"已经跑过一遍的库"——断点续跑的世界里，绝大多数件是缓存命中，f.done 一在，函数在兜底那一行之前就返回了。

这一行是什么时候落到短路之后的？翻版本：v6 重写抽帧函数那一次（为修 OCR 早停与静态图流）。首跑时它没暴露——首跑没有缓存，每一件都走完整路径，时长全算齐了；后面几轮 backfill 在缓存之上重建账本，这 339 件的时长从此再没被算过：

  • 首跑（无缓存）：dur 算齐 → 账本完整 855.5h；
  • backfill（缓存齐全）：339 件的 dur 从未计算 → 重建的账本把它们写成空 → 756.3h。

值得停一秒的是这个失败的形态：它不是"算错了"，是"没算"——而没算的字段不报错、不崩溃、不进日志，它只是空。若无总账对账，这 339 个空格可以安安静静躺到某天有人问"为什么这条视频没有时长"。

2. 修复：把回填写成一道 pass

修复没有在原地挪那一行——修在了唯一看得见全部账目的地方：汇总（rollup）的收口处，加一道独立的回填 pass：


def _backfill_durs(items):
    """dur_s 缺失件补时长：media.json 缓存 → ffprobe 现测（并写回缓存）。"""
    for it in items:
        if it.get("dur_s"):
            continue                 # 只碰缺失件，已有值一个不改
        ...                          # 缓存优先 → 现测兜底 → 写回 media.json

四个设计点，各自对着一个教训：

点一句话
只补缺失回填不是重算，是补账——已有值零改动（事后逐件对账 changed=0）
缓存优先 + 写回一次回填之后，缓存层也补齐；pass 可重入，第二遍接近零成本
修在收口处分支里打补丁会漏（哪条路径又会绕过？）；汇总前一道 pass 管全部
自带回执汇总日志一行：DUR-BACKFILL fixed=335——修复动作本身可对账

收官跑（job-162）：计时 0.5 分钟，fixed=335，总时长从 756.3 恢复到 855.5h。335 = 339 − 4——剩下 4 件是 ffprobe 也读不出的坏件，时长如实留缺。账上允许有缺口，不许有不明缺口：这两者在数字上长得一样，区别在于后者没人说得清缺在哪、为什么缺。

3. 插曲：对账尺自己的账

回头说 848.8 那笔。它来自一条对账命令：


awk -F'\t' 'NR>1 {s+=$4; n+=$3} END {printf "总时长=%.1fh 件数=%d", s, n}' 台账.tsv

NR>1 的本意是跳过表头。可这份底稿没有表头——第一行就是数据：影视散片，3 件，6.2 小时。于是：

  • 848.8 + 6.2 = 855.0 ✓
  • 2285 + 3 = 2288 ✓
  • 94 + 1 = 95 ✓

三个数字同时归位——这就是破案和"碰巧对上一个"的区别：一个数对得上可能是巧合，三个数同时解释得通，才是找到了机制。剩下的 0.5 小时零头，是组级台账四舍五入与逐件精确的和差——账目世界里，连"对得上"都是有刻度的。

对账尺自己也会错，这件事不新鲜；新鲜的是它错的姿势：它以为自己在跳表头，其实在吃第一行数据——和你对账的那本账，用的是同一份"想当然"。

4. 收束

三句话带走：

  • 短路省的是计算，不是契约。 改动"提前返回"型优化时，问一句：被跳过的路径上，还有谁欠着什么——字段、记账、缓存写回。优化改的是控制流，契约要在新的控制流上重新证明一遍。
  • 隐性劣化的哨兵是总量对账。 字段空掉不会崩，总账会变小；总数、总时长、总条数是三根最便宜的探针。这次是"855.5 对 756.3"抓出来的——没有这步对账，339 个空格能躺到明年。
  • 修复的完成形态是回填 pass：清单驱动、只补缺失、缓存写回、缺口留痕、自带回执。附带一条：对账之前先验尺——这次是尺子自己先被审了一遍，才轮到数据。
