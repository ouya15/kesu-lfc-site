36 拒绝面：把「不许删」编译成机器语法

2026-09-13·连载

前情：13《怎么会没有备份》是全系列最疼的一篇；14《治理四梁》把纪律从自觉降维到结构；22《换乘触发器》写过"服务化的本质是权力收窄"；35《判断力上浮》刚把编排层的调度器删掉。这一篇回到治理最底下的一块砖：把文档里的一句"不许"，编译成机器语法。

一句话："不许"如果只活在文档里，就等于没有；拒绝面 = 动词面（删除动词不存在）+ 对象面（受保护清单）+ 理由面（403 要能读）+ 验收句（能一行复现）。

引子：一句活在文档里的「不许」

字幕事故那一夜之后，治理宪法里多了一条铁律：受保护目录的删改，任何会话不得在会话内直接执行，必须走 mission 立项——清单、回收箱、回滚三件套，一个不能少。

这条铁律写得很硬。但它活在两个地方：文档里，和 agent 的自觉里。此后一天里它一次没被违反——不是因为机器拦住了谁，而是因为没人恰好想删。

复述一遍纪律，和兑现一次纪律，中间隔着整个机器。

1. 先弄清威胁模型：不是黑客，是「顺手」

设计的第一问不是"怎么防"，是"谁可能删"。

答案不是攻击者，是持着 token 的本机 agent——有能力、低成本、无监督、失忆。删除也不会以"删除任务"的形态出现；它更可能长这样：大扫除顺手清掉的"闲置"目录、脚本演化中多出来的一个 rm -rf、工具链重构时被吃掉的边角料。事故的形态是常识性的，不是对抗性的。

所以拒绝面的目标不是防住外科手术，而是把"顺手"从这个可能性空间里搬走——外加一条：每次尝试都留下证据。（边界也如实声明：不解析符号链接、不拦间接拼接；本机单人环境，防呆不防外科手术。）

2. 拒绝面三件：动词、对象、理由

动词面：系统里根本没有"删除"这个动词——DELETE 一律拒绝。不设白名单不是偷懒，是原则：留一个删除动词，就是留一个洞。真要删的走 mission 立项，那是另一条有三道开关的路。

对象面：受保护清单=铁律原文的逐字映射（仓库根 + 六个子目录），匹配收进一个纯函数：分隔符归一、大小写不敏感、段匹配，payload 深度遍历——嵌套对象、数组里的字符串，全都算。清单刻意只覆盖铁律写明的范围：拒绝面不宜过宽，多拦一分就多一分误伤，铁律升级了清单再跟着扩。

理由面：403 不许是黑箱，要回 {reason, matched}——"删除面不存在：受保护目录删除走 mission 立项"这样的句子。拒绝的可读性，就是未来的可审性；一条读不懂的 403 等同于 500。

3. 验收句：机制的第一公民

33 号文说过，提案的完成标准是每条过成本审判。机制的完成标准类似，且更具体：每件都能一行复现。

所以验收句在写代码之前就先写好了：


curl -X DELETE :8322/notes/1   →   403 + 可读理由 + 审计留痕

当天实测：直删被 403 拦下并写明原因；越权路径同样留痕；正常读写、原有回归全绿。整个实现零 schema、一个中间件、只挡写不挡读。

4. 一个反直觉：它谁也拦不住

这份功能，拦不住任何"真想删的人"——对方手里有 shell，绕过 API 就是了。

它的价值不在拦住，在这三件事：把"顺手"从这条路径上搬走；把"发生过的尝试"变成审计里的一行；把治理从"记得住"变成"不需要记得"。 机器化治理的收益，从来不是防住蓄意者，而是让无意的、赶时间的、会失忆的操作者，不可能再"意外"犯错。

结语

现在，每一条"不许"都该过一遍四问：动词面在哪？对象面在哪？理由在哪？验收句是什么？ 答不全的，就还只是文档里的一句话。
