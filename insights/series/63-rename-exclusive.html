63 换名要独占：一次 WinError 5，与一句没说出口的平台假设

2026-09-14·连载

前情：41《装得上》写的是安装期的"官方假设 Linux"，59《白名单之外》写的是格式层的"清单假设 mp4"；这一篇是同族的运行期版本——配方假设"rename 对读者无感"。它也与同一个上午的 62 直接相邻：1.6.5 修完账本竞态，顺手把写账升级成原子写，几分钟后，这笔顺手的债就到期了。

一句话："tmp + rename 是原子写"是一句 POSIX 常识，它默认了"换名对读者无感"——在 Windows，换名要读者先点头；一次几毫秒的句柄占用，被一次没有重试的换名升级成了作业的死刑。修复=退避重试 + 兜底留痕。

0. 现场：失败的不是活儿，是账房的字

62 的账本竞态修完（1.6.5），活体验证通过（09:10 同秒双发工单正确分号）。重发补跑作业——job-156，562 个单元的同一批活儿。

跑到 55.4%（OCR 311/561），被判 failed。作业的 error 字段里躺着的不是它自己的异常：


[WinError 5] 拒绝访问。: 'D:\study-videos\reports\win-node-jobs.json.tmp'
                     -> 'D:\study-videos\reports\win-node-jobs.json'

异常逃逸，采集器进程随之消亡。

看清楚这份判词：干活的是它，死的也是它——但错误跟它的活儿毫无关系。它只是在每个单元干完时往账本抛一行进度；某一行的背后，账本自己要换一次名字，换名被拒了；异常顺着记账线程爬到作业的生死判定上——账房先生写坏一个字，把犯人判了死刑。

而且失败的是一次毫秒级的冲突——某个读者正好在这几毫秒里开着账本。一次瞬时的不让路，被一次没有重试的换名，升级成了一次永久判决。

1. 解剖：POSIX 无感，Windows 要独占

"换名"哪来的？1.6.5 的顺手升级。修竞态时，save_jobs 被升级成标准原子写配方：


tmp = path.with_name(path.name + ".tmp")
tmp.write_bytes(data)
os.replace(tmp, path)          # 原子换名：读者永远看不到半写文件

这在 Linux 上是无懈可击的常识。但 os.replace 在 Windows 上落到 MoveFileEx(..., MOVEFILE_REPLACE_EXISTING)——要"盖掉"一个正被打开的目标文件，Windows 要求所有打开它的句柄都授权了 FILE_SHARE_DELETE；Python 的 open() 不给这个权限。 任何一个读者只要恰好在这几毫秒里开着账本，换名就被拒：WinError 5（拒绝访问）或 32（共享冲突）——在 Python 里都映射成 PermissionError。

读者是谁？两路，都很无辜：

  • 我们自己的监控——Prometheus 每 5 秒抓一次 /metrics，而 L2 指标是从账本派生的：每 5 秒，有一只眼睛要打开一次账本；
  • 夜间的观察脚本，同样以读者的身份路过。

写者呢？日志泵——长作业的每行输出回写一次账本（回填进度就靠它一行行报出来）。写入跟着回填的脚步 × 读取每 5 秒一次，撞上只是时间问题。

有一个讽刺要写下来：那只眼睛是前一晚刚装上的（监控栈 1.6.1）。把可见性架在账本上，也就把监控本身变成了写者的对手——你装上了眼睛，眼睛成了那根压倒账房的稻草。

那 1.6.4 为什么没有这个病？那时 save_jobs 是直写（open("w")），直写不需要删除权限——读写共享模式互相容忍，代价是读者可能读到半写文件。原子写不是免费的：它把"读者看到的完整性"换成了"写者对读者的独占要求"——在 POSIX 里这笔交换对读者无感（rename(2) 换的是名字，握着老文件的读者继续读，没人需要点头），在 Windows 里，这笔交换要每个读者签字。

2. 修复：重试、兜底、留痕

1.6.6（90fa731），三行判据落成一个函数：


def _atomic_write(path: pathlib.Path, data: bytes, retries: int = 6) -> None:
    """原子写：tmp+replace，撞 Windows 并发读句柄（WinError 5/32）时短退避重试；
    重试全败则退化直写（锁内调用；1.6.4 及以前生产行为）并留痕。"""
    tmp = path.with_name(path.name + ".tmp-swap")
    tmp.write_bytes(data)
    err = None
    for i in range(retries):
        try:
            os.replace(tmp, path)
            return
        except PermissionError as e:
            err = e
            if i < retries - 1:
                time.sleep(0.05 * (i + 1))
    audit("system", "atomic_write", str(path), "fallback", str(err)[:80])
    path.write_bytes(data)

三个设计点，一个比一个值钱：

  • 退避重试——读者握句柄是毫秒级的事；0.05+0.10+0.15+0.20+0.25≈0.75 秒的重试窗口，足够跨过任何一次抓取。瞬时冲突的正确待遇是等等它，不是判它死。
  • 兜底降级到直写——重试全败就退回 1.6.4 的老行为：宁可要一次"可能被读脏"的直写，不要一次"作业死掉"的失败。原子的最高优先级是别崩，其次才是别撕裂。
  • 留痕——降级必须写审计（atomic_write fallback + 原错误）。降级可以，静默不行。

接入两处：save_jobs（账本）与 fs_put（上传）——同一张配方，同一堵墙，一起换了。守卫空窗部署（09:19）+ noop 冒烟 PASS（job-159）；重发的补跑作业换成 job-160，走完了全程。

顺带一句业界注脚：跨平台的原子写，重试是标配——Node 的 fs.rename 重试循环、编辑器与构建工具的 atomic write 实现，都带同款退避。这不是 Windows 的 bug，是 Windows 的语义；配方要过这道门，就得把这条语义写进实现里。

3. 对照：同一次换名，两个平台

POSIX（Linux / macOS）Windows
换名的实现rename(2)MoveFileEx(REPLACE_EXISTING)
目标正被读者打开读者无感——握着旧 inode 继续读需要每个句柄授权 FILE_SHARE_DELETE
Python open() 的授权不涉及不含 FILE_SHARE_DELETE
撞上后的表现不存在这个冲突PermissionError（WinError 5 / 32）
修复不需要退避重试 + 兜底直写 + 留痕

一句话：同一张"原子写"配方，语义假设完全不同——POSIX 版假设"没人需要同意"，Windows 版要求"人人需要同意"。

4. 收束

  • 平台假设不会写在配方里。 "tmp + rename 就是原子写"是一句 Linux 常识，它默认了"换名对读者无感"——这是 POSIX 没说完的半句话。搬运配方时，该问的不是"这个 API 跨平台有没有"，是"它依赖了哪个平台没写出来的前提"。（41/59 同族第三例：安装期假设 Linux、格式层假设 mp4、文件层假设 rename 无感。）
  • 修复会引入新的失败条件。 1.6.5 顺手把写账升级成原子写——几分钟后，正是这个升级把作业判了死。修完一处，要问一句：这个改动自己在什么条件下会失败。
  • 瞬时冲突不许判永久死刑。 重试是最便宜的宽容：读者占用毫秒级，退避 0.75 秒就跨过去了。全败要兜底 + 留痕——降级可以，静默不行。
  • 诚实备注：共用的错误通道没有修——记账线程的异常仍会爬到作业的生死判定上；1.6.6 只是让这类异常几乎不再发生。写下，不修；下一次现场若再遇到它，它就是候选。
