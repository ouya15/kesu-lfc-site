评测与自省

222 三层评测：为 agent 流水线建立"每次改动有判决"的机制

2026-08-09·obp

日期：2026-08-09

说明：文中公司名为脱敏代称（希腊神话人物名），业务场景已泛化，数字为约数。

一、背景与需求

问题：补丁循环

#223 CRSS 系统的评级 rubric 迭代到 v5.1 时，已经连续打了四轮补丁：v3 → v4 → v5 → v5.1，每一轮都是"发现偏差 → 打补丁 → 全量重跑"（全量一次数小时）。每一轮改完都只有"看起来改好了"这一个证据。

停跑前最后一次审计给出了决定性证据：

  • v5 判为误判的 5 家公司在 v5.1 全部未降级——prompt 里的文字防御规则（"年报正面数据/资料页不是较高依据"）模型基本不执行，5/5 落空
  • 新抽查 6 家"较高"，3 家由低质资料页条目撑起

结论：补丁路线结构性失败。根因不是哪条规则写得不好，是没有闸口——任何改动都没有可量化的结论，改坏了没有自动拦截。搜索引擎团队的标准做法是 golden 回归（事故样本转回归用例，改动必跑），这套方法论需要迁移到 agent/LLM 流水线上。

需求定义

  • 每次改查询模板 / 过滤阈值 / 实体规则 / 评级 rubric，都有可量化的结论（指标回退即拦下）
  • 评测必须"跑得起"：规则层 0 API、全量、秒级——跑得起才是机制，跑不起只是文档
  • 覆盖两条链路：merge 过滤链路（确定性规则）+ agent 研究链路（开放式语义，LLM 判断）

二、总体架构：三层互补

层判什么成本速度可信度
规则层过滤/保留判定、schema 合法0（离线）秒级确定性 100%
judge 层摘要 vs 原文事实一致性、评级合理性1~2 次 API/条分钟级高，有偏差需缓解
人工层报告端到端是否"可交付"每周 10 条慢最高（锚点）

设计依据：规则层覆盖不了开放式语义对错；judge 层补上语义判断但自带偏差（位置偏差/自我偏好/冗长偏好——业界已实证，JudgeFlip 翻转率 57-100%）；人工最可信但贵。三层互补，不是用一层打天下。 三层缺一层，结论都不可信：没有规则层，每次改动成本高企；没有 judge 层，语义对错无闸口；没有人上层，新失败模式无人兜底。

工作流：


代码/配置改动 → unittest 全绿？→ 否 → 拦下
                  └ 是 → run_eval 规则层（秒级、0 API）
                          ├ 指标回退？→ 拦下 + 附 bad case
                          ├ judge 层 nightly（评级对齐，~15 次调用）
                          └ 月度人工抽样 → bad case 回灌 golden

成本实测：规则层 0；judge 层评级对齐每轮 15 次调用（分钟级）；人工每周 10 条 × 10 分钟。三层全开月度成本约一杯咖啡。

三、数据模型：golden set

golden 是评测的基准，也是治理资产——事故样本转回归用例，与开发样本分离，防过拟合到评测集。

item_labels（条目级标注）


{
  "company": "Athena S.A.",
  "category": "legal",
  "title": "...",
  "url": "https://...",
  "content": "...",
  "label": "irrelevant",      // relevant | irrelevant | border
  "note": "标注理由",
  "source": "archive"          // archive 真实事故 / auto 机器标注 / constructed 构造
}

三值标签语义：

  • relevant：真实风险事件，必须保留
  • irrelevant：资料页/注册信息/同名噪声/行情页，必须滤掉
  • border：妥协条目（资料域名但命中风险词），按 relevant 对待但单独统计，不算相关正样本

规模 139 条：irrelevant 72（E 清理审计快照 68 + Athena 事故 4）/ relevant 52（六类别正样本每类 4 条 + 记录站豁免抽样 25 + 必收录回归 3）/ border 15（妥协条目）。

构建纪律：

  • MUST_INCLUDE 必收录机制：历史上误杀过的真实事件（如某零售巨头资料页上的集体诉讼）锁进 golden，不参与抽样——抽样再公平也不能漏掉误杀历史实证
  • 抽样控制：妥协条目 15 条封顶；记录站豁免每 host 8 条、总量 25 条（防 goodjobsfirst 一家独大）

rating_labels（公司级评级期望）


{
  "company": "Hera AG",
  "expected_risk": "中",       // 5 级制
  "expected_trend": "平稳",
  "evidence_note": "标注依据（证据链/裁决记录）",
  "source": "audit+user_decision"
}

15 家构成：audit 锚点 4 + 误判样本 4 + 重评实证 6 + border 混同 1（VOLTANEO，实体拆分后定稿）。source 白名单（audit/rerate/border/auto/audit+user_decision）保证标注来源可审计——这条白名单本身被测试强制校验，防止来源字段乱写。

四、规则层：确定性回归（0 API、秒级）

机制

对 golden 每条执行确定性过滤链（低质判定 + 实体过滤），判定该条目是否应被保留，与标注比对：

  • precision = 保留且 relevant / 保留数（宁可漏场景的护航）
  • recall = 保留且 relevant / gold relevant 总数（别把真风险筛掉）
  • 误杀逐条看（gold relevant 中被丢弃的）
  • 结果写 history.json（时间/版本/git commit/指标），趋势对比，"没变差"才能合入

数据

基线：TP/TN/FP/FN = 67/71/1/0，precision 0.985 / recall 1.000 / F1=0.993，噪声率 0.014，RISK_KW 救回 15 条 border 条目全保留。FN=0：相关/border 零误杀（硬约束）。

唯一 FP：Athena 行情标题（"Athena SA Stock Price Today"）——设计边界：股价文章属评级规则层职责（"股价分析不是较高/中依据"），不是输入清理对象，由 judge 层兜底。

决策记录

  • FN=0 是硬约束：宁可噪声率上去，不可把真实风险滤掉——保险场景损失不对称（漏掉一条真实破产信号 > 多一条噪声）
  • RISK_KW 一票保留：命中风险关键词（诉讼/违约/泄露/召回等）的条目一律保留，哪怕它在资料页域名上。实证：某零售巨头 yellowpages 条目是 数千万条数据泄露集体诉讼，一刀切会误杀
  • 测试抓到生产 bug：PROFILE_URL_PATTERNS 双斜杠（f"/{path}" 产生 //profile 永不命中）——路径模式防御形同虚设，单测回归后修复。规则层评测的正确性依赖底层规则本身的正确性，单测与评测是互补关系

五、judge 层：评级对齐

机制

对 rating_labels 每家：读该公司 items 证据集 → build_report_prompt 评级（与生产同款 prompt 与流程）→ 输出等级 vs golden 期望 → 判定：

  • 精确一致：输出 = 期望
  • 相邻一致：5 级尺度（低/较低/中/较高/高）相差 1 档
  • 不一致：相差 ≥2 档
  • border（期望为"?"）不算分

数据：基线演进

版本精确一致相邻一致说明
v5.1（基线）0.50（7/14）0.86（12/14）rubric 未动，fresh API 调用
v6.0（锚点首轮）0.667（10/15）0.867（13/15）VOLTANEO 拆分定稿后 15 家
v6.0 + Hestia 修正0.6670.933标注修正收益 +0.07
v6.1（实质程度限定）0.6670.933仅 Hera 一个硬不一致
v6.2（锚点冲突修复）0.6670.933复测实证口径

评测反噬标注：标注质量是评测上界

两轮评级对齐中，模型对真实证据的评级持续高于 golden 期望——初看是模型错了，打印推理链逐条核对后，模型有据，标注标错了：

  • Hestia：期望"较低"，模型评"较高"。证据：流动比率约 0.8、净债务/EBITDA 5 倍+、Z-Score 约 2.5 灰区。期望来自更早一轮人工审计的叙事（当时只有正面新闻），真实财务信号是评测跑起来后暴露的。用户裁决期望改"中"，修正一条标注，相邻一致 +0.07。
  • Hera：期望"较低"，模型评"较高"。诊断推理链：投机级（B 档）、Debt/EBITDA 数倍、EBIT/利息覆盖接近零，但无违约/无破产/无流动性危机（现金约 €1.7 亿 + 自由现金流约 €4 亿 + RCF 额度），重大诉讼已结案（约 €2000 万已付 + 2016 最高院基本胜诉）——模型是权衡后判"中"，不是误判。期望改"中"，修正生效。

规律：评测对的是标注。模型被实证正确时，修正的是标注而不是系统。 评测不只验证系统，也验证自己的答案——标注质量是评测上界，反噬标注是模式不是偶发。

决策记录

  • 复测取稳：judge 单次输出有方差（Apollo 复测较低/中波动；Hera 4 次运行 3 较高 1 中），关键变更公司必须复测取稳，单次数字不作数
  • 评测结论必须重跑实证：曾基于一次批量口径推断"相邻满贯"，期望修正后重跑即被证伪（另一家公司的方差顶替了唯一不一致位）——数字要重跑，推断不作数
  • meta 提取失败是已知失败模式：Apollo/Demeter/Zeus 多次出现评级 meta 提取返回 None/"?"，单独重试成功——管线错误（提取失败）与模型输出（评级）要分开归因，不能把提取失败当评级结果

六、锚点迭代：rubric 升级与两类新缺陷

v6.0：锚点示例替代抽象规则

v5.1 审计实证抽象防御规则模型不执行（5/5 落空），rubric 改为"事件形态→评级"具象先例，内置 7 条锚点（泄露+集体诉讼→较低、拆售→较低、破产公开+净资产恶化+未决索赔→高、公司解散→高、资料页→低或较低、纯正面→低、速动 0.3+流动负债大→较高）。

结果：Apollo 较高→较低（拆售锚点修复）、Hercules 较高→中（2 档差缩到 1 档）、Ares/Demeter 转精确一致，对齐 0.50→0.667 / 0.86→0.867。

评测抓出锚点误套（v6.1 修复）

副作用：Hera 被"流动性恶化"锚点推高（两次复测稳定），实际依据只是轻微运营指标（质量投诉率上升）。改进引入了回归，评测体系当场抓住——没有基线数字，这类回归要等下一轮审计才暴露。

修复：流动性锚点加"证据须达实质程度"限定——流动性恶化必须落在具体财务指标（流动比率持续 <1、速动 <0.5、净债务/EBITDA >4、利息保障 <3、Z-Score 灰区及以下）且无缓解迹象；单年波动或轻微运营指标（质量投诉率/产品偏差率上升、单年 EBIT 下降、成本上升、供应链调整、常规专利诉讼）不是较高/中的依据，此类仅评较低，除非同时伴随债务违约或流动性危机的实质证据。

锚点冲突（v6.2 修复）

Zeus 复测 3 次低/较低/高——同输入 3 档差。诊断：verif.com 信用评估报告（含"公开破产程序+未决索赔"实质内容）同时命中两个锚点——"资料页→低"（域名是资料页）与"破产程序→高"（内容含实质风险信号），模型随机选边。根因是两层脱节：输入层 RISK_KW 一票保留保护了这条，评级层资料页锚点却贬低它。

修复：资料页锚点加限定——"资料页/注册信息域名上的条目若内容含实质风险信号（破产/违约/诉讼/制裁/监管处罚等），按实质信号评级，不适用本条"，与输入层 RISK_KW 对齐。复测验证：修复后有效运行均评高。

异常结果四分法（诊断方法论）

边界/异常结果不要只看分数，打印模型推理链，分四类：

现象判定处理
复测跳档（同输入高/中波动）judge 方差复测取稳，别改规则
复测稳定地错rubric 缺陷修 rubric
同输入命中两条互斥锚点锚点冲突检查锚点互斥，加限定
模型有据、期望不符标注错修 golden，不是修系统

四类处理动作完全不同，分错类就是拿对类的方法改错类的问题——把方差当回归修，越修越坏。

七、人工层：月度抽样锚点

  • 每周抽 10 条端到端（真实公司跑全链路）：① 该保留的保留了？② 该过滤的过滤了？③ 摘要事实可核？④ 报告可交付？
  • 抽样选法：分层 + 主动学习（被 judge 判不定、被规则卡在边界、新公司先抽）
  • 结果回灌：新增 golden case / 修正 judge rubric / 修正边界阈值

人工层回答的是另外三层答不了的问题：golden 之外的新失败模式。评测的"判决"有上界——规则与 judge 只能判"见过的错"，新失败模式只能靠人工兜底，所以人工层不可省。

八、验证与现状

  • 130 个自动化测试全绿（含 test_eval 8 例、test_source_quality 17 例——后者抓到 //profile 生产 bug）
  • 规则层 F1=0.993、FN=0（0 API 成本，改动必跑）
  • 评级对齐精确 0.667 / 相邻 0.933（15 家基准，复测实证口径）
  • 评测执行成本：规则层 0；评级对齐每轮 15 次调用（分钟级）
  • 公开版（crss-public）：golden 为合成数据（34 条条目标注 / 5 家虚构公司 + 1 家纯评级期望），评测逻辑与私有版一致

九、已知局限

  • golden 只含已有 URL，不衡量"检索到没搜到"（召回上界未知）——评测不覆盖检索召回质量
  • judge 单次输出有方差：单次对齐度数字本身会波动，结论必须多次运行/复测取稳
  • meta 提取存在已知失败模式（None/"?"），重试处理，需与模型输出分开归因
  • 精确一致 0.667 受 4-5 家 1 档差限制（Apollo 方差、Hercules、Prometheus、Zeus 冲突余波等），提升需路径 C/D（维度化评分 / 独立裁判）

总结

三层评测把"改坏了没"从感觉变成数字：规则层 0 API 秒级兜住确定性回归，judge 层 15 次调用给出对齐基线，人工层每周 10 条兜住新失败模式，bad case 全回灌 golden。运行中最重要的发现不是指标变好了，而是评测开始修正评测自身——两轮反噬标注证明标注质量是评测上界，四类失败模式的分法让每个异常都有正确的处理动作。这套体系迁移自搜索引擎的 golden 回归方法论，实测成本约一杯咖啡/月。
