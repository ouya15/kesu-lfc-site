27 别教模型做事——pythia 的诞生与归档

2026-05-07·obp

日期：2026-05-07

背景

2026 年 4 月底，在迭代 OBP prompt 体系时，产生了一个想法：能不能把"需求澄清"这件事标准化？于是创建了 pythia——一个苏格拉底式需求澄清引擎，定义了五个追问维度（动机、边界、隐含假设、逻辑一致性、替代方案），试图教 AI 按照固定框架帮用户厘清模糊需求。

创建它的初始动机之一是省 token：如果能用一个轻量模型来引导追问流程，就不需要每次都依赖高阶模型的通用推理能力。

问题

pythia 创建后，一直没有被触发过。回顾原因：

  • 聪明的模型本身就是 pythia。当你对 Deepseek V4 或 Claude Opus 说「我有个想法但没想清楚」，模型自然会启动各种思考策略——追问动机、探测边界、挑战假设——这些思维动作是内化在模型能力中的，不需要外部 Skill 文件来"教"。
  • 显式框架反而限制了模型的思考空间。pythia 把追问固定在五个预设维度里，而模型本身可能跳出这个框架、想到更巧妙的角度。好的 prompt 是给模型空间，而不是给它栅栏。
  • 交互模式不匹配。pythia 是对话式多轮追问，而用户（我）更偏好 brief 批阅模式——"我写完你来处理"，效率远高于来回问答。
  • 省 token 的动机本身有问题。需求澄清是思维展开的关键阶段，恰恰是最不该省钱的环节。pythia 自己的核心信条第一条就写了「需求澄清不能用劣质模型」，但它的存在本身就是在试图用一个静态文本替代模型的动态推理。

方案

归档 pythia，从 skills 目录和发布映射中移除。将这次经历沉淀为一条判断原则。

放弃了什么：五个追问维度的标准化框架。这些维度本身没有错，但把它们写进 Skill 文件让 AI 照着执行，是对模型能力的低估。

保留了什么：pythia 的思想——"不要急着给方案，先追问"——这个意识已经内化到日常交互习惯中，不需要一个 Skill 来承载。

结论

别教模型做事：人机协作的边界在移动

这个 case 暴露了一个认知陷阱：人习惯性地把自己的思考方法编码成指令，试图"教"模型如何思考。这在模型能力不足的时代是合理的——你需要用 prompt engineering 弥补模型的短板。但当模型已经足够聪明时，这种做法就变成了班门弄斧。

判断标准是：这件事是模型做不好需要我教，还是模型本来就会但我不放心？

  • 模型做不好的：领域知识注入（如 cost-ops 的集群分析规则）、个人偏好约束（如写作风格规范）、流程性操作（如日记创建的具体步骤）——这些值得写成 Skill。
  • 模型本来就会的：如何追问、如何拆解需求、如何做批判性思考——这些写成 Skill 是多余的，甚至有害。

而且这个边界在快速移动。今天模型做不好的事，半年后可能成为基本能力。这意味着 Skill 体系需要定期"减法审计"：不是看哪些 Skill 该加，而是看哪些 Skill 已经被模型能力淘汰了。

pythia 是第一个被淘汰的。不会是最后一个。

观察：不是所有抽象都有价值——当底层能力已经覆盖时，中间层抽象就变成了负担。这和软件工程里"过早抽象"的反模式是同构的。可串联 #26（Skill 治理膨胀税）。
