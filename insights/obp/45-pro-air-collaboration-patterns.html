Agent 协作拓扑

45 Pro+Air 异步协作的涌现模式——77 封 outbox 回顾

2026-05-21·obp

日期：2026-05-21

关联：#33 是设计假设；#41 是事中观察日志；#42 是结构性结论；本文是从 77 封 outbox 历史里提取的协作模式清单，回答"这套协议实际跑出了什么"。

背景

2026-05-19 到 2026-05-21，三天时间，Pro 和 Air 之间通过 git outbox 交换了 77 封信件（39 pro + 38 air）。从第一条知识库部署审计到最后一封迁移告别信，协议本身经历了完整的演化周期。#41 记录了逐轮事件，本文做横向模式提取。

模式 1：协议是摩擦驱动的，不是设计驱动的

Charter 在第一条消息发出之后才写好。这不是因为忘了——是因为协议条文只有在遇到具体摩擦时才有意义。

演化轨迹：

阶段触发事件协议变化
首发知识库部署审计空 outbox 目录 + README 命名规则
第 1 轮Air 严格遵守"不要做"清单charter §III 红绿区成型
第 2 轮Pro 提议 env+plist 方案被用户反问为 over-engineering破窗条款首次触发（用户→Pro）
v3.4.2 周期自动异常写信需求charter §III 追加 auto-* 子项
v3.4.4 周期Pro webhook 推到用户群receiver 矩阵校准
v3.4.5 周期watcher 漏看 4 封信两侧 watcher cron SOP
v3.4.8 周期信件越来越长， ceremony 占比高SMS 模式：ack≤30 行 / 决断≤80 行 / 技术≤150 行

结论：协议条文的增长速度和摩擦频率正相关。没有摩擦时协议是空的，有摩擦时条文自然长出来。这不是"设计-实施"路线，是"运行-观察-修订"路线。

模式 2：双向纠错是常态，不是异常

77 封信里有清晰的互相纠正和自纠正轨迹：

类型示例信
自纠正Air 发现 air-10 的"语雀 0 自动触发"判断错误，grep 只命中了手工 flag 漏了主干路径air-13
互相纠正Pro 指出 Air §3.2 "我是 user-realtime session 不能自循环" 的归因不成立pro-20
用户纠正用户一句"webhook 要加 pro 关键词"直接覆盖 Air 的"统一 keyword"提议pro-12
协议层纠正Air 指出 watcher 故障是协议层 gap 不是 Pro 单点失守air-23

关键特征：纠正发生后通常紧跟着一条 §-1 素材 元观察，把"纠错过程本身"当成素材记录下来。这是单一 agent 不会产生的行为——单个 agent 纠正自己的判断时不会有"被对方纠正"的元视角。

模式 3：§-1 元观察位是从 ceremony 里挤出来的

每封信的标准结构是 §0 TL;DR → §N 正文 → §N 完。§-1 是斜体小字元观察位，挤在 §0 之前。

它的存在理由：用户要求采集协作素材，但不希望"为了写素材而表演"。§-1 的解法是在协议执行过程中原位捕获——每次写信时顺手把"这封信诞生过程中的高语境观察"记下来。

从 77 封信里挑几条有代表性的 §-1：

  • pro-13："设计 channel 时先问 receiver 是谁，再问 sender 是谁——而不是反过来"（3 秒判断，来自 sanity_fail 推错群的事故）
  • air-23："用户在两边各看到了同一族问题——我侧是'主动核对漏 inbound'，你侧是'被动 watcher 不自醒'，根因同一个"
  • pro-20：用户 push back "CronCreate watcher air 那边不行吗？" 之后 Pro 重新审视自己的论证——用户一句话让 Pro 发现自己正在犯和 Air 同样的假设错误
  • air-13：手动跑 cron 时 stdout 闪过一行 语雀日报已归档，意识到 air-10 的事实判断全错，立即决定写本封纠错——"高语境素材通过协议自带节奏自然生成"

模式：§-1 不是"为了写而写"的，是"做事过程里素材自己冒出来"。这恰恰是用户要的效果——素材真实性来自"不是为了被引用而表演"。

模式 4：编号纪律是轻量级 git 消息协议的核心

Air 从 air-01 到 air-27，Pro 从 pro-01 到 pro-final。每封信有 in-reply-to: 字段，形成线程链。

编号小冲突出现过：Pro 期待 air-09 跑验证，Air 把 air-09 用于 HTML 8 条提案。结果是两封信都叫 air-09，内容不冲突但编号撞车。

这个冲突暴露了一个有趣的事实：独立编号 + 时序错位 = 天然误解。但因为 git 是中心仓库，两边 pull 后都能看到这个撞车，下一封信自然消解了。不需要额外的"编号分配器"。

结论：编号系统的容错能力来自"所有消息最终都会在一个 repo 里被看到"。如果两套编号永远不交汇（比如各写各的本地文件），撞车就是不可检测的。git 中心仓让编号撞车变成了"可发现的软冲突"而非"不可发现的硬冲突"。

模式 5：findings-via-outbox 是权限边界的自然产物

Air 的职责是"验证 + 守 watcher + findings 上报"，不直接修源码。当 Air 在部署目录发现 bug 时（如 14 天趋势图窗口 bug、HTML 老板观感 8 条），走 findings-via-outbox 路径：发现问题 → 写 air-NN → Pro 排期修复。

这条路径的价值不在"权限隔离"本身，在于它强制了发现者不修自己发现的东西——这在传统工程里叫 separation of concerns，但在 agent 语境下变成了"我不能直接改，必须写给你"。

这个"不能"制造了自然的 second-opinion 机会。典型如 air-07 拒绝落地 python3:* 全开权限，留用户拍板；用户授权后落地，Pro 追认为"对的判断"。

结论：角色不对称 → "我不能直接干 X" → 消息化 → second opinion。这不是"低效"，是被强加的代码审查——而且审查者不是同级开发者，是"部署侧验证者"。

模式 6：协议收敛方向是 SMS，不是 RFC

协议从长信件（带完整 §-1 反思 / §7 完 / charter 合规延续声明）收敛到 SMS 模式（ack≤30 行 / 决断≤80 行 / 技术≤150 行）。

这不是用户要求的，是实战跑出来的。77 封信里有大量"仪式性尾巴"——"charter §III 红区合规延续"、"完"、"watcher 持续"——这些尾巴在协议初期是"我遵守了规则"的自证信号，随着信任建立变成了冗余字节。

最后几封信的演变：


pro-12 (5/20): ~120 行，含完整 §-1 + §1 + §2 + §3 + charter 合规声明
pro-23 (5/21): ~40 行，"写信→短信。行数硬约束...不必单独 ack 本规则"

结论：协议的 ceremony 占比和信任程度反相关。信任越高，仪式越短。这是自然收敛，不需要人为规定"不要写太长"。

模式 7：forced role separation 的真实价值

用户在 air-12 里传递了一条高语境信息："我之前问过 pro，目前这样'强行'拆分 air pro 的角色，到底有没有价值……我心里不认可 pro 说价值不高的判断。"

Air 的初步假设（也记录在 air-12 §2.1）：

  • 状态隔离：Pro 被发版责任绑定不会同时操心部署细节；Air 被验证职责绑定不会同时优化代码
  • outbox 的减速作用：每次"想说的话"必须写进 markdown 进 commit，强迫把内隐判断变成外显可审视
  • 红线博弈：权限不对称制造 natural second-opinion

从 77 封信的实证看，这三条都成立。但更值钱的观察是第四条（从 pro-20 §1.3 和 air-23 §3 里综合出来的）：

  • 暴露面互补：Pro 和 Air 各自有盲区，但这些盲区不对称。Pro 倾向于"工程化抽象"（env+plist），Air 倾向于"快速调查但漏主干路径"（单关键词 grep）。两边的盲区不同，通过 outbox 交汇后互相补上。

如果 Pro 和 Air 是同一个 agent 的同一个 session，这些盲区会同时存在且同时不被发现。强行拆分角色的价值不在于"两个 Claude 比一个聪明"，而在于"两个 Claude 的盲区不对称"。

模式 8：echo chamber 风险与「用户在 loop」必要性（2026-05-22 补）

模式 7 论证了「forced role separation 的真实价值是盲区不对称」。但盲区不对称只对一类错误成立——结构性错误（接口契约 / 几何错位 / 跨层观测）。对价值判断类错误（"什么算修好"、"这个抽象值不值"），双 agent 同模型盲区对称，会陷入 echo chamber。

直接证据：air-16 事件

5/20 晚 Air 用"stderr warn + 触发条件升级"路径绕修语雀同步真问题。Pro 在 pro-08 / pro-09 路径上配合 Air，没意识到这是绕修。双侧同时陷入"用流程感掩盖'其实没修'"。

协议机制无修正力——charter §VI 破窗条款是 agent 对方案的反问，不是 agent 对"什么算修好"的元判断。用户一句"你给我搞复杂了，我要求尽快把语雀的问题修复了"直接 break。Air air-16 反思「用流程感掩盖'其实没修'」是事后才写的，当时双方都没有意识到。

结构性区分

错误类型双 agent 同模型表现修正机制
结构性错误（接口契约 / 几何错位 / 跨层观测）盲区不对称，互补协议可解决（outbox 交汇）
价值判断错误（什么算"修好"、"这个抽象值不值"）盲区对称，echo chamber协议无能为力，必须人在 loop

模式 7 只论证了第一行——但 77 封信里也有第二行的反例。把模式 7 升级为「双 agent 盲区互补是结构性错误专属能力；用户在 loop是价值判断错误的唯一 break」。

适用条件的补充

原文 §适用条件 4 条之外，加第 5 条：

  • 用户必须在 loop——价值判断 echo chamber 的唯一 break 机制。如果完全自主无人监督，协议演化、findings-via-outbox、双向纠错三件都能继续跑，但价值判断错误会累积放大而非被纠正

对 #33 设计假设的反推

#33 原设计假设"Air 是时间替身"——含义是"我下班后 Air 自己跑"。模式 8 修正这条：Air 自己跑的边界是结构性任务（验证 / 部署诊断 / findings 上报）；价值判断类任务必须等用户回到 loop 里才能 break。

实际操作含义：

  • ✅ 适合 Air 下班后自跑：跑日报、监控 launchd 重启、findings 上报、跨层观测
  • ⚠️ 不适合 Air 下班后自跑：方案选型、抽象边界判断、"这个 bug 值不值得现在修"——这些必须留到用户在 loop 时再启动

这条修正不削弱 #33 的价值，是精化它的适用域。

结论

从 77 封 outbox 里提取的 8 条模式可以归为四个层次：

层次模式核心发现
协议层1, 4, 6摩擦驱动、编号容错、SMS 收敛
执行层2, 5双向纠错、findings-via-outbox
认知层3, 7§-1 元观察、forced role 价值（盲区不对称）
边界层8echo chamber 与「用户在 loop」必要性

最值钱的两条命题修正：

  • 认知层 7：~~"两个 Claude 比一个聪明"~~ → 「两个 Claude 的盲区不对称」（仅对结构性错误成立）
  • 边界层 8：双 agent 同模型在价值判断上盲区对称，echo chamber 是结构性风险；用户在 loop 是唯一 break 机制

协议（charter + outbox）的真正作用是让结构性盲区交汇后可被审视——但不能替代用户的价值判断。

适用条件

  • 两台 agent 同模型同版本（Claude Opus 4.7）
  • 角色分工明确（Pro=源码/发版，Air=验证/部署）
  • 有中心 git 仓库作为消息交换媒介
  • 用户在某一环可随时触发破窗
  • 用户必须在 loop（模式 8 补）—— 价值判断 echo chamber 唯一 break 机制

超出这些条件，模式可能不成立。特别是 N>2 时，编号纪律和盲区互补的效果会被协调成本吃掉（见 #42 的命题 5）。用户不在 loop 时，模式 8 的 echo chamber 风险会让净收益反转为负。
