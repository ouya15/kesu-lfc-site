Skill 橱窗

103 一个出版社，多个编辑部——多 session 协作的内容与分发分离

2026-07-30·obp

日期：2026-07-30

状态：活文档——CMS 与发文体系仍在边跑边迭代，本文随这套编辑部/出版社模型的演进持续更新，此处是某一阶段的快照。

背景

老剧《编辑部的故事》里，那间乱哄哄又较真的编辑部，是我特别喜欢的一个意象。稿子在编辑部里被判断、被打磨、被卡下来或放出去，然后才轮到印刷发行。

我本地有不少技术 insight——个人知识管理的、搜索性能的、Skill 工程的、记忆系统的，散落在不同的项目仓库里，在不同的 session 下写的。对应的公开博客，持续整理发布中。

问题

判断内容是一回事，把它发出去是另一回事。最早我让一个 session 做选稿、脱敏、排版、上线的全流程工作。

一个 session 全包的问题，是太重。选稿要内容判断，脱敏要知道每个域里什么算敏感，排版上线要熟工具和节奏——它得同时装着所有域的上下文，每次编辑内容都得先喂一大段背景，整个 session 越来越重。

而扛得越多，每份上下文就越薄。做发布的那个 session，并不写搜索性能那些文章，它没有那个域的上下文。它不知道某个缩写是内部系统名，正如一个不跑口的编辑，认不出某篇稿子里的化名指的是谁。脱敏扫描是按关键词匹配的，可关键词清单本身也是那个 session 列的——它列不出它根本不知道的词。

方案

把"判断内容"和"执行发布"拆开。一个出版社，多个编辑部。

编辑部是每个域的 session：它陪着我写那个域的文章，知道哪句话在域内是敏感的、哪个数据断言要核实、哪几篇该合成一个系列。它负责内容正确性、分级、把修订落到源文件，以及语义级脱敏的第一遍——识别"什么词在这个域里是敏感的"。

出版社是一个专职的发布 session：它不判断内容对不对，管节奏、跨专栏一致性、目录、站点 CMS 评审、规则级脱敏的第二遍（关键词扫描），以及守住最后一道人工闸——发之前我亲自过目。两层脱敏是纵深防御：任何一层漏了，另一层还在。

接口也标准化了。单篇新稿走"付印稿"：编辑部把稿子做到齐清定（内容定了、脱敏过了、分级标好了），写一份结构固定的交接文档，出版社拿到只管排版上线。整个专栏的批量策展走另一份活文档，逐篇定级、标风险、写意见。出版社的工作于是从"读懂全部文章"塌缩成"处理 N 份结构一致的管道文档"——它不需要懂内容，只需要相信编辑部已经把内容这一关把住了。

落到一个 skill：lfc-publish

上面这套东西不是一次性的默契，它固化成了一份两个角色都会读的操作手册——一个叫 lfc-publish 的 skill。它不是出版社的私产：编辑部读它，知道自己该交出什么；出版社读它，知道怎么接。分工钉在同一份文档上，规则改了只改一处。它规定三样东西。

一是内容的单一事实源（SSOT），拆成三层：markdown 原文是内容源，catalog 是元数据（状态、标签、专栏归属），站点 HTML 是预渲染的 CMS 表现层。三层之间改动只能从上游往下游流，但人不用直接改上游：在 CMS 表现层评注，修订同步回 markdown，HTML 再重渲染——SSOT 由这条回路保障。

二是收稿协议，也就是编辑部和出版社之间的两个接口：整条专栏的批量策展走一份活文档，逐篇定级、标风险、写意见；单篇急稿走一份"付印稿"。付印稿结构固定——稿件信息（标题、分级、风险、脱敏状态、专栏归属）、编辑部策展意见、出版社待办清单、一份只增不改的变更日志。编辑部写完就是齐清定，出版社照待办执行，把每步记进日志，一次交接的完整轨迹留在一份文档里。

三是两层脱敏的规则清单。规则级的关键词清单住在 skill 里，随每次复盘加词，配合编辑部在域内做的语义脱敏。

还没想清楚的

这个分离的核心，目前我信的是这句话：内容判断需要域上下文，分发执行需要一致性和工具，这两样很难在同一个 session 里同时强。 但它还没被足够多的场景验证，下面几个问题我自己也还没想透。

我问自己最多的一个：两个 session 面前坐的是同一个人，这种分工是不是过家家？目前的回答是：分工管的不是信任，是认知负荷——强制一次显式交接，就强制一次"把隐性判断写下来"，跟自己下棋也算练习是一个道理。但这个答案站不站得住，得等这套流程再跑一段时间。

另一处边界是软的：CMS 预览工具编辑部也能用，出版社真正独占的只有生产目录的写权限、规则级脱敏和 push。也就是说，分离靠的是权限和纪律，不是工具隔离。这样够不够稳，也是开放问题。

还有一个套娃：这篇讲编辑部/出版社怎么运作的文章，本身正是走它描述的这套流程发出来的。李冬宝们大概会觉得，这很编辑部。
