103 一个出版社，多个编辑部——职责分离，而不是 session 分离

2026-07-30·obp

日期：2026-07-30

状态：活文档——本文经历过一次认知更新（2026-08-07）：从"物理 session 分离"改写为"职责分离 + 文档化上下文"。

关联：中心文章 #106（lfc-studio CMS 系统）；簇内 #221（批量 merge 方法论）。

问题：全包太重

我本地有不少技术 insight，散落在不同项目仓库、不同 session 下写的。最早让一个 session 做选稿、脱敏、排版、上线的全流程——太重：它得同时装着所有域的上下文，每次编辑内容都得先喂一大段背景。

最初的答案：把"判断内容"和"执行发布"拆成物理上分离的两个 session——编辑部（每个域一个）和出版社（专职发布）。

实践观察：物理分离很少发生

实际跑下来，单独的编辑部 session 很少出现。日常工作基本都在出版社这一个 session 里完成——写内容、评审、脱敏、发布。编辑部角色只在很大的项目里才单独开 session，小稿子都是随手写、随手发。物理分离只在上下文重到无法文档化时才需要——那是大项目才有的场景，目前还没遇到。

上下文不是"装在脑子里"，是"外化到文档里"

为什么一个 session 能扛住当初认为必须分离的活？因为上下文不需要记住，只需要能查：

  • catalog.json 存元数据——哪篇什么状态、什么标签、归哪个专栏，不用记
  • ROADMAP/BACKLOG 存状态与纪律——做到哪、下一步是什么，不用记
  • columns/ 存策展——专栏怎么排、每篇的导读，不用记
  • 批注系统存评审意见——评了什么、改没改，不用记

上下文被文档外化了。session 的"上下文薄"问题不是靠物理隔离解决的，是靠让信息可查解决的。这是 #106 那套 CMS 的核心贡献：记忆负担从 session 转移到了文档。

那分离还剩什么价值：职责边界

物理 session 分离弱化了，但"判断内容"和"执行发布"这两件事的职责分离没有消失，它落在了权限和纪律上：

  • 谁有 catalog 的写权限、谁能 publish——只有出版社
  • 编辑部只写文章 md，其他一概不碰
  • 两层脱敏的纵深防御——语义级第一遍（域内敏感词），规则级第二遍（关键词扫描）

落到 skill：lfc-publish

职责说明书固化成了一份文档——lfc-publish。它不是出版社的私产：编辑部读它知道自己该交出什么，出版社读它知道怎么接。规则改了只改一处。它规定三样东西：SSOT 三层（分层细节见 #106）、收稿协议（付印稿是单篇交接文档，策展活文档是整专栏的逐篇定级表）、两层脱敏的规则清单。

另一个套娃：这篇讲编辑部/出版社怎么运作的文章，本身正是走它描述的这套流程发出来的。这很编辑部。
