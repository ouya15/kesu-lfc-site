评测与自省

223 CRSS 系统：一百七十多家企业的信用风险监控平台

·obp

说明：文中公司名为脱敏代称（希腊神话人物名），业务场景已泛化，数字为约数。

〇、系统定位

本文系统是个人使用的分析 demo，场景设定为保险行业的买方信用风险监控。非公司内部生产系统，数据为个人整理，公司名与业务场景均已代称化。

一、背景：保险承保决策依赖什么

保险的业务形态：企业把货卖给买方，如果买方拒付或破产，保险公司按约定赔付。因此承保部门的核心工作，是判断买方企业的信用风险——这家公司未来一年会不会破产、会不会拖欠、会不会因为制裁或供应链中断而无法履约。

业务侧维护一份 一百七十多家买方企业的名单，分布在多个国家，涵盖零售、制造、化工、汽车等行业。风险监控要覆盖六个维度：法律（诉讼/判决）、监管（处罚/资质）、财务（违约/流动性/杠杆）、网络安全（泄露/攻击）、经营（供应链/停摆/重组）、ESG（环境/劳工/治理）。

这个场景有三个特性决定了系统设计：

  • 持续性：不是一次性尽调，是持续监控——风险事件是增量发生的，新诉讼、新破产程序、新制裁每天都在出现
  • 可追责：承保决策要记录依据，报告里的每条证据必须能点回原始来源
  • 成本敏感：一百七十多家 × 6 维度的人工盯法是几个人力，系统化的目标是单人可维护

二、总体架构


companies.csv（一百七十多家名单）
    │
    ▼
研究引擎（DeepSeek 原生 web_search，6 类别多轮自搜）
    │   输出 items/{company}.json —— 唯一真相源，git 管理
    ▼
治理层（三道闸）
    URL 溯源校验 → 实体消歧 → 低质条目过滤
    │
    ├──► 报告层：评级（5 级×3 趋势）+ 六类别研判，rating_history 追加式
    ├──► 知识库：SQLite 派生查询层（FTS5 中文检索，幂等重建）
    ├──► 展示层：静态报告站点（搜索/筛选/评级轨迹/下载）
    └──► 评测层：golden 回归 + 评级对齐（离线，0 API 成本）

技术栈刻意保持最小：Python 标准库 + requests + openpyxl，零外部服务依赖。一个人维护的系统，依赖越少越容易活。

四个关键设计决策：

① JSON 是唯一真相源，SQLite 是派生查询层。 所有业务数据以 JSON 文件存储（git 管理、可 diff、可回滚），SQLite 数据库文件 gitignore，随时可从 JSON 幂等全量重建。这个选型经过一次设计辩论：最初用户质疑"只有一百七十多家公司，文本存储够了，数据库的价值在哪？"——结论是查询层价值 ≠ 数据量：单文件 SQLite 让"跨公司聚合、中文全文检索、按风险筛选"从写脚本变成一条 SQL，而且存储方案没有被锁定（查询层不变，只换 sync 目标）。

② items-as-state。 每家公司一个 JSON 文件，条目以 URL 为唯一键。增量 = 新 URL − 已有 URL，旧条目永不覆盖。这个模型让中断恢复、增量更新、审计追溯全部变得简单——没有数据库状态需要同步，文件本身就是状态。

③ 证据可溯源是硬性约束。 报告中的每条证据必须能落到 items 中某条具体条目的 URL 上，评级越高，这个约束越强（"点不出证据就不给高"）。

④ 评测闭环是改动闸口。 任何规则/阈值改动先跑离线评测（规则层 0 API、秒级），指标回退即拦下——没有"看起来还行"这个说法。

三、数据模型

items 文件（每家公司一个）


data/research/items/{company_slug}.json

顶层字段：company、rounds（研究轮次记录）、raw_results（模型自搜的原始搜索结果，溯源比对的依据）、hallucinated_dropped（溯源丢弃统计）、entity_filtered（实体过滤统计）、coverage（六类别覆盖度）、elapsed_s、items（条目数组）、report_meta（评级 meta）、report_md（完整报告）、rating_history（评级轨迹）、last_updated。

条目字段只有五个：category（legal/regulatory/financial/cyber/business/esg）、title、url、summary（中文摘要）、date（发布时间，部分缺失）。

字段刻意少——真相源只存"搜索证据 + 摘要"，一切派生内容（评级、报告、翻译）都从这五个字段生成，保证单一事实来源。

rating_history（评级轨迹）


rating_history: [{overall_risk, trend, date, reason}, ...]

追加式记录：每次评级 + 理由 + 日期，永不覆盖。评级变动可审计、可回溯——"这家公司为什么从较高变成中"，翻历史就有答案。

审计快照

数据操作（清理/拆分）先写快照再执行：data/audit/low_quality_removed.json（每条被删条目的公司/标题/URL/理由）、entity_mixup_removed.json。任何删减可回滚、可追溯。

四、研究引擎

切换决策：Tavily → DeepSeek

第一版使用 Tavily 搜索 + 8 个并行研究代理，每家 4 类查询，跑通后两天免费额度耗尽。当时设计文档里保留了一条备选："DeepSeek 原生 web_search，暂不实现，保留可能性"——Anthropic 兼容端点，搜索在模型服务端执行，本地只收发 prompt 与搜索结果（查询词 + 原始 URL 列表）。

切换成本是一行 base_url，24 小时内完成，成本降一个数量级。决策记录：查询模板与搜索后端解耦的设计，让供应商切换成为配置级变更——如果当初把 Tavily 写死在代码里，额度耗尽那天至少要修两天。

多轮自搜机制

研究阶段每家公司一个 prompt：列出六类别、要求模型先核实基本面（财务概况、信用评级、债务流动性），再按类别搜索。搜索由模型在服务端自主执行：查询词由模型自选，每家公司 3~5 轮搜索，客户端拿回全部查询词与原始 URL 列表。

这个架构有一个重要推论：本地无法约束服务端的搜索过程（模型选什么查询词、搜几次都不可控），只能在结果端防御——URL 校验、实体过滤、低质过滤三道闸全部落在结果处理上。这是后来 VOLTANEO 混同事故的根源分析（见第六节）。

批次协议与容错

  • 20 家/批、5 并发、--resume 幂等断点续跑：中断任意恢复，不重跑已完成公司（以 items 文件存在为完成标记）
  • 空结果三态信封：空/重试/放弃分开处理，不再静默吞掉
  • 补救轮固化：失败单家自动收集 → 批量补救 → 直到全量 0 错误

全量一百七十多家约半小时，11 批 + 7 轮补救完成，2500+ 条条目，0 错误。先把"跑不完"解决，才有资格谈质量。

五、幻觉治理：URL 溯源硬校验

问题

LLM 搜索返回的条目存在系统性幻觉：模型会编造 URL。摘要可能是真实搜索结果（模型确实搜到了相关信息），URL 是模型生成的。首轮实测部分公司溯源丢弃率超过 30%——意味着报告中三成证据点不回原始来源。

机制

  • 逐字比对：条目 URL 必须与模型自搜的原始搜索结果（raw_results）逐字比对，通过才入库
  • 丢弃统计：未通过进 hallucinated_dropped，丢弃率 >30% 的公司触发补搜
  • 报告轮强制：prompt 硬性条款——"证据必须能落到 items 中某条具体条目的 URL 上，点不出证据就不给高"

代价

约 3% 真实但检索不到的旧闻被误丢。接受——宁可真新闻被丢，不能让假证据进承保报告。

决策记录

为什么用校验而不是提示词？当时还没有证据，后来的实证给出了答案：v5.1 的 prompt 文字防御规则（"年报正面数据/资料页不是较高依据"）在审计中 5/5 落空——模型基本不执行 prompt 里的防御性文字。对不可靠输出的防御，校验永远比祈祷可靠。提示词是愿望，校验是机制。

六、实体消歧：score ≠ 实体

Athena 事故

名单里有家波兰公司 Athena。搜索结果里大量"Athena"指向一家同名律所。模型把时装公司的行情页写进律所的风险报告——score 相关度全对（文本确实相关），实体错了（是另一个 Athena）。

机制

召回层的实体身份校验：

  • 公司别名清单 + 内容信号过滤（命中风险关键词：诉讼/破产/召回/制裁/违约等才放行）
  • 拿不准的 fail-open 白名单：宁可保留疑似条目，不误杀真实事件

核心认识：搜索的 score 衡量的是文本相关度，不是实体一致性——这两个维度必须分开防御。

VOLTANEO 变体

URL 校验通过、实体过滤通过，但内容实际属于另一家公司（Hermes Energy）：搜索按别名召回，模型在服务端未复核实体身份。这是 Athena 事故的变体、新失败模式——根因在服务端搜索过程不可控，本地只能在结果端叠加防御（URL 校验 + 实体过滤 + 低质过滤三道闸），最终靠人工拆分 + 补搜定稿。

七、数据治理

约两成 数据战役

一次全量重研究后，条目数 2500+ → 2000+，约两成。第一反应是重跑。改为先做 URL 级差异分析：1900+ 条旧 URL 未复现。关键词宽筛（破产/违约/制裁/诉讼等）筛出 800+ 条有实质信号嫌疑的，按低质域名黑名单过滤后回灌 800+ 条（打 recovered 标记），合并重评，证据池回到 2800+ 条。

决策记录："重跑前先读中间产物"——差 18% 不一定是随机波动，先搞清楚系统性差异再动手。这条后来第二次救命：3 层改 5 层评级前，半程 148 家中间结果差点被当作过期数据扔掉，被保留后成为 5 层设计的实证样本。

条目层治理（路径 E）

审计发现低质域名条目（资料页/注册信息，标题即公司名、内容为工商档案、无日期）仍支撑"误判较高"评级。三通道识别：

  • exact 域名黑名单：约 50 个 hostname（verif/pitchbook/tracxn/zoominfo/crunchbase/dnb/kompass 等），hostname 精确匹配弃子串
  • URL 路径模式：资料页特征路径
  • 内容形状兜底：summary 无实质内容时按标题判定

防误杀设计（一票保留 + 豁免）

一刀切会删掉真实事件。三条防线：

  • RISK_KW 一票保留：命中风险关键词（诉讼/违约/泄露/召回等）的条目一律保留，即使它在资料页域名上。实证：某零售巨头的 yellowpages 条目实际是 数千万条数据泄露集体诉讼，一刀切会删掉真实事件
  • 记录站豁免：goodjobsfirst/osha/szse/canadiantire——标题=公司名但内容是实质记录（集体诉讼案卷/行政处罚），必须保留
  • border 妥协条目单独统计：资料域名+风险词的条目标 border，不算相关正样本，但不删除

结果：清理 60+ 条低质条目（约 50 家公司），审计快照可回滚；定向重评证据悬空的 30+ 家 → 十几家评级变化。实证：Artemis 较高→低（资料页撑评级的误判被修复）、Hades 较低→高（公司已解散，交易主体消亡）、Zeus 中→高（公开破产 + 自有资本近 0.4 跌至不足 0.1）。

5 层定义（rubric 现行条款）

评级由最严重 1-2 条事件的绝对严重程度决定——条目数量绝不是加高依据（30 条轻微报道仍评较低，1 条实质事件也可能评高）；已结案事件按结局后的实际影响判断。

  • 高（证据必须落到 items 具体 URL）：债务违约 / 破产程序 / 流动性危机 / 重大制裁或出口管制实质阻断交易 / 核心生产长期停摆
  • 较高（实质性威胁的前兆已出现，未触发高的条件，必须能指出证据条目）：大规模召回致核心产品停摆、巨额罚款动摇流动性、多起重大诉讼叠加、重大数据泄露引发大额索赔、连续亏损且债务高企、关键供应链长期中断、重大监管调查进行中
  • 中（存在可关注信号，必须能指出具体信号）：中等规模罚款、单起重大诉讼/仲裁、部分产品召回、一般性合规违规、轻度财务恶化迹象、供应链一般扰动
  • 较低（轻微/孤立，不影响偿付与履约）：小额罚单、单条负面报道、常规运营事件带轻微负面色彩、历史遗留小问题、已解决事件的余波
  • 低：无实质负面证据，正常经营。"低风险是正常状态而非负面评价，没有实质负面证据就评低，请敢于给低"

锚点示例（v6.0 起）

抽象防御规则被审计证伪后（v5.1 防御规则 5/5 落空），改为"事件形态→评级"具象先例，rubric 内置 7 条：

  • 数千万条数据泄露集体诉讼 + 网安事件公告 → 较低（泄露已修复/赔付在途，现金流未受实质冲击；叠加监管吊销执照/银行抽贷/大额判赔才升较高）
  • 大股东拟出售/业务板块拆售 → 较低（拆售是股东战略选择；进入清算/停业/资不抵债分配才升级）
  • 破产程序公开 + 自有资本连续大幅恶化（0.38→0.09）+ 未决索赔 → 高
  • 公司已解散（strike-off 注销）→ 高（交易主体消亡）
  • 证据仅是第三方资料页/注册信息 → 低或较低（限定：资料页域名条目内容含实质风险信号时按实质信号评级——v6.2，Zeus 实证）
  • 全部为正面新闻/业绩发布/股价分析 → 较低或低（"敢评低是正常状态"）
  • 速动比率 0.3、现金远小于流动负债 → 较高（限定：流动性恶化必须落在具体财务指标——流动比率持续 <1、速动 <0.5、净债务/EBITDA >4、利息保障 <3、Z-Score 灰区及以下，且无缓解迹象；单年波动或轻微运营指标不是较高/中的依据，此类仅评较低——v6.1）

方法论决策

分布是指示器，抽查审计才是判定。 用户质疑"用分布拟合校准是否本身有偏颇"——如果这一百七十多家公司客观上就是高风险的，拉平分布会扭曲真实信号。定案：分布预期只作 prompt 内的异常指示灯（高 5-12%、较高 15-25%、中 30-40%），代码无任何硬性拉平；真正手段是证据抽查审计（抽 12 家较高公司逐条核对 top3 信号）。

九、评测体系：补丁循环的终结（方法论详见 #222 三层评测）

停跑审计

rubric 连打四轮补丁（v3/v4/v5/v5.1）后，用户喊停："去业界搜索参考、扩展思路，而不是一直给 prompt 打加强补丁。"停跑前最后审计：

  • v5 判误判的 5 家较高在 v5.1 全部未降级——prompt 文字防御规则模型基本不执行
  • 新抽查 6 家较高，3 家由低质资料页撑起

结论：补丁路线结构性失败。双通道调研（tavily + DeepSeek 原生搜索交叉验证：Buyer Grade 1-10、校准停止条件、judge self-preference bias 实证）产出五条升级路径：E 条目清理 / A 评测先行 / B 锚点示例 / C 维度化 / D 独立裁判。

golden set

139 条条目级标注（三值：relevant 52 / irrelevant 72 / border 15）+ 15 家公司级评级期望。标注来源：审计快照 + 现有证据池抽样 + 历史事故样本（Athena 等）。抽样有纪律：妥协条目 15 条封顶、记录站豁免每 host 8 条/总量 25 条；必收录回归案例不参与抽样——历史上误杀过的真实事件（某零售巨头资料页上的集体诉讼）锁进 MUST_INCLUDE，防止公平抽样埋掉教训。

规则层（0 API、秒级）

对每条 golden 跑确定性过滤链（低质判定 + 实体过滤），指标：precision/recall/F1 + 误杀逐条看。基线：F1=0.993、FN=0（相关/border 零误杀，硬约束），唯一 FP 是 Athena 行情标题（设计边界：股价文章属评级规则层职责，不是输入清理对象）。

评级对齐层（judge）

对 15 家 rating_labels 跑真实评级，判定精确一致/相邻一致（5 级尺度差 1 档）/不一致。基线演进：

v6.2（锚点冲突修复）0.6670.933

评测反噬标注（两轮实证）

第一次：一家公司模型评"较高"，golden 期望"较低"。初看模型错了，打印推理链后查证据——流动比率约 0.8、净债务/EBITDA 5 倍+、Z-Score 约 2.5 灰区。模型有据，标注标错了（期望来自更早审计叙事，当时只有正面新闻）。用户裁决期望改"中"，修正一条标注，相邻一致 +0.07。

第二次：同剧本的另一家。诊断推理链：投机级评级、数倍杠杆、利息覆盖≈0，但无违约/无破产/无流动性危机，重大诉讼已结案——模型是权衡后判"中"，不是误判。期望改"中"，修正生效。

规律：评测对的是标注。模型被实证正确时，修正的是标注而不是系统——标注质量是评测上界。 评测不只验证系统，也验证自己的答案。

锚点迭代抓出两类新缺陷

  • 锚点误套（v6.0 副作用）：Hera 被"流动性恶化"锚点推高，实际依据只是轻微运营指标 → v6.1 加"证据须达实质程度"限定
  • 锚点冲突（v6.2）：Zeus 的 verif.com 条目同时命中"资料页→低"与"破产程序→高"两个锚点，模型随机选边，同输入评分差 3 档 → 资料页锚点加"内容含实质风险信号按实质信号评级"限定，与输入层 RISK_KW 对齐

异常结果四分法（诊断方法论）：方差（复测取稳，别改规则）/ 稳定回归（修 rubric）/ 锚点冲突（查锚点互斥）/ 标注错（修 golden）——四类处理动作完全不同，分错类就是拿对类的方法改错类的问题。评测结论必须重跑实证：基于单次批量口径推断"相邻满贯"，重跑即被证伪——数字要重跑，推断不作数。

十、增量更新：items-as-state

周增量轮（设计 D1-D5 用户评审后落地）：

  • 增量 = 新 URL − 已有 URL，URL 去重保留旧条目
  • 无新增公司的批次完全零改动（连时间戳都不变）——幂等性验证
  • 有新增 → 报告轮带【上次研判】锚点（截断 4000 字符）+ 反锚定规则（"按当前证据修正并说明理由"）→ rating_history 追加 → diff Excel（变化汇总/新增明细两 sheet）→ 站点重建
  • 单家失败只记录不阻断

效果：周增量轮从全量数小时降到约 30 分钟。不重跑，是最大的性能优化。

十一、展示层与知识库

  • 静态报告站点：纯静态 HTML，零运行时依赖——搜索、风险筛选、类别 AND 筛选、排序、评级轨迹卡片（history 末 8 条）、本周更新速览、单家详情页（六类别条目全量）、下载区（全量 Excel 三表 + 单体 HTML）
  • 知识库：SQLite + FTS5 trigram 中文全文检索（trigram 是中文分词的正解，默认 tokenizer 不支持中文）、按风险/类别聚合查询、CSV 导出；db 文件 gitignore，随时从 JSON 重建

十二、验证与现状

  • 一百七十多家 / 2800+ 条已核实风险条目（E 清理后口径），六类别
  • 130 个自动化测试全绿（逻辑层/增量轮/知识库/解析器/评测/条目治理），测试抓到过生产 bug（URL 路径模式双斜杠永不命中）
  • 规则层 F1=0.993、FN=0；评级对齐精确 0.667 / 相邻 0.933（15 家基准）
  • 全链路可回滚：git 每步 commit + 审计快照
  • 公开版 crss-public：数据脱敏为合成数据（虚构公司），评测逻辑与私有版一致

十三、已知局限与后续方向

  • golden 只含已有 URL，不衡量"检索到没搜到"（召回上界未知）
  • judge 单次输出有方差，关键结论需复测取稳；meta 提取存在已知失败模式（约个别公司/轮）
  • 财务信号依赖模型搜索提取（非结构化）——后续方向：接入免费结构化财务数据（SEC EDGAR XBRL / akshare）交叉验证锚点指标（流动比率/净债务 EBITDA/利息保障/Z-Score 都是现成的锚点条件）
  • 评级精确对齐 0.667 受 1 档差限制（Apollo 方差、Hercules、Prometheus 等），提升需路径 C/D（维度化评分 / 独立裁判）

总结

CRSS 把"LLM 输出的不可靠性"当作默认假设来设计：每一层都假设对方会犯错——模型会编 URL、搜索会混实体、评级会虚高、规则会误杀、标注会标错——然后每一层都留校验、留回滚、留证据。系统规模不大，但每个环节都有可验证的工程决策和真实事故支撑，评测体系（golden 回归 + 评级对齐）为"每次改动有判决"提供了机制保证。
