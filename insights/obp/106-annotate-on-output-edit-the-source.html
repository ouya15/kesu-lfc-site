工作室札记

106 在成品上批注，改的却是源头——lfc-studio 的所见即所得评审

2026-08-05·obp

日期：2026-08-05

状态：活文档——lfc-studio 边用边改，本文随它的形态更新，此处是某一阶段的快照。

背景

#103 讲了内容和分发分离：编辑部管内容、出版社管发布，中间守着最后一道人工闸——发之前我亲自过目。这篇讲那道闸具体长什么样。

过目需要所见即所得。我要看的是文章在站点上最终的样子——排版、代码高亮、专栏归属都对，而不是去读一份 markdown 源文件在脑子里脑补渲染结果。但"看成品"和"改内容"之间有个天然的矛盾，这个矛盾是这篇的起点。

问题

站点是三层派生结构（#103）：markdown 是内容源，catalog 是元数据源，HTML 是渲染产物。规矩是改动只能从上游往下游流。

矛盾就在这里：我过目时看的是最下游的 HTML，发现问题的现场也在 HTML，但我不能在 HTML 上改——改了渲染产物，下一次 build_site 重新生成就把我的手改冲掉了。所以早期的流程是割裂的：在浏览器里看，发现问题记在脑子里或聊天窗口里，再切回编辑器找到对应的 markdown 位置去改。看的地方和改的地方是两处，中间靠人脑做映射。

更麻烦的是评审意见本身没有落点。一条"这句太啰嗦"飘在聊天记录里，没有锚在具体哪句话上，也没有状态——改没改、搁置了还是采纳了，过两天就对不上号。评审是有生命周期的，可聊天窗口给不了它生命周期。

方案

lfc-studio 把"看"和"改"重新缝到一起，办法是让批注落在表现层，但改动流回源头。

它是一个本地服务器，serve 渲染好的 site/，同时往每个页面注入一层批注 widget。我在页面上选中任意一段文字写批注，批注锚在那段引文上，存进 annotations.json。这一层完全活在表现层，不碰源文件——所以它不违反 SSOT，HTML 重新生成也不影响批注，因为批注根本不在 HTML 里，是运行时叠上去的。


~/lfc-staging/                     评审工作台
├── studio.py                      批注 + 实时渲染服务器（serve site/，注入 widget）
├── annotations.json               批注存储（引文锚点 + 生命周期状态）
├── catalog.json                   元数据 SSOT（状态 / 标签 / 专栏归属）
├── _tools/
│   ├── make_catalog.py            扫源仓库 → catalog.json
│   ├── build_site.py              catalog + md → site/
│   └── publish.py                 生成公开版 → 推线上
└── site/                          studio serve 的渲染产物（只读观察面）
    ├── index.html
    └── insights/<repo>/<slug>.html

回路取代纪律。 关键的一步不是批注，是批注之后。我读批注，改的是上游 markdown，然后 build_site 重渲染，页面自动刷新，批注气泡重新锚回新的引文——一条"表现层发现问题 → 源头修改 → 重渲染"的回路。SSOT 不是靠"别碰下游"这条纪律守住的，是靠这条回路的拓扑守住的：下游是只读的观察面，写操作都被引导回上游。人可以放心地盯着成品挑刺，因为挑出来的刺有一条固定的路径回到源头去改。

这条回路里现在还站着一个 agent——批注不是被程序直接写回 markdown 的，是我读了批注、判断了、手动改的 md。这一环是人和 AI 的判断，不是自动同步。它该不该做成全自动（批注触发 agent 直接改源、改完实时回渲），我还没想清楚。

交互是被真实使用逼出来的。 widget 的每一处设计都对应一个用起来才暴露的痛点。批注气泡最初浮在引文右边，挡住正文——改成落在正文列两侧的空白里，用细折线指回原文，左右均衡分布。输入框最初一点别处就自动消失，导致想复制段文字批注框就没了——改成生命周期由保存/取消手动结束，且允许多个框并存。批注详情面板最初设计了"待选方案""最终决定"一堆字段，却唯独不能编辑批注正文本身——砍掉没人用的字段，把正文改成可编辑。三个改动指向同一条：工具的每个元素都得有人真的在用，为"看着完整""有气势"而加的东西是负担，发现了就砍。那个被砍的"范围"下拉框还有一层单独的教训，见 #101 不要在信息最贫乏的时刻提问。

这里有个分工得说清楚：widget 的代码是 AI 写的，这些痛点和取舍是我在用的过程中撞出来、逐条提出来的。工具不是我手搓的，判断也不是 AI 替我做的。

还没想清楚的

这套东西现在能用，但有两处我没想透。

一是回路里那个 agent 环节该不该自动化。现在是人读批注、手动改 md，慢但可控；曾经设想过批注直接触发 agent 改源、实时回渲，做成一个同步指针。自动化省去手动搬运，但也把判断从人手里拿走了——评审的价值恰恰在那次判断上，自动化会不会把它冲淡，我没有答案。

二是工具的归属边界。lfc-studio 是出版社（发布 session）建的，但它编辑部也能用——预览和批注不是发布专属能力。#103 里已经点到：CMS 共用之后，出版社真正独占的只剩生产目录的写权限、规则级脱敏和 push，分离靠的是权限和纪律，不是工具隔离。那么 lfc-studio 到底算谁的工具？也许它本就该是中立的第三方基础设施，谁都能用，边界只画在写权限那一道。这个还没定。
